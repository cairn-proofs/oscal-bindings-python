# Requirements Document

## Introduction

This feature adds property-based tests (using the Hypothesis library) to the oscal-bindings project. The tests exercise the public API surface — the parser functions, the `OscalDoc` facade, the back-matter builders, and `validate_element` — by asserting invariants that must hold across many inputs rather than a handful of hand-written examples.

Two categories of inputs drive the tests. Real OSCAL documents are fetched from two remote, commit-pinned corpora (NIST `oscal-content` and AWS `oscal-content-for-aws-services`) and seed round-trip and facade properties, optionally with structural mutations. Because NIST publishes no Mapping Collection example, a third, local-only, opt-in corpus supplied through an environment variable covers that document type on developer machines; CI does not configure it, so CI exercises 7 of the 8 OSCAL document types. Synthetic inputs are generated by Hypothesis strategies only for the back-matter builders and for `validate_element` leaf types; no full synthetic OSCAL document is ever generated.

This is a test-only feature. No source under `src/oscal_bindings/` is modified. Changes are limited to test configuration, test code, and test-support fixtures.

## Glossary

- **PBT_Suite**: The collection of property-based test modules, fixtures, and support code added by this feature, executed under the existing pytest/Hatch harness.
- **Corpus_Fetcher**: The test-support component that downloads, pins, caches, and exposes OSCAL documents from the remote corpora to the PBT_Suite.
- **NIST_Corpus**: The remote corpus at `https://github.com/usnistgov/oscal-content`, pinned to a specific commit SHA, providing example documents for the 7 OSCAL document types NIST publishes examples for: catalog, profile, component-definition, system-security-plan, assessment-plan, assessment-results, and plan-of-action-and-milestones. NIST publishes no mapping-collection example, so the NIST_Corpus contains no mapping-collection document.
- **AWS_Corpus**: The remote corpus at `https://github.com/awslabs/oscal-content-for-aws-services`, pinned to a specific commit SHA, scoped to the `component-definitions/` subdirectory.
- **Local_Corpus**: An optional, developer-supplied corpus read in place from the absolute path held in the `OSCAL_BINDINGS_LOCAL_CORPUS` environment variable (either one OSCAL JSON file or a directory of them). The Local_Corpus is never fetched, cached, copied, or committed, and exists to cover document types absent from the NIST_Corpus and AWS_Corpus (currently mapping-collection).
- **Local_Corpus_Variable**: The `OSCAL_BINDINGS_LOCAL_CORPUS` environment variable.
- **OSCAL_Root_Key_Filter**: The rule that keeps a JSON file only when the file's single top-level key is one of the 8 OSCAL document root keys.
- **Corpus_Cache**: The local, git-ignored directory where fetched corpus documents are stored for reuse across test runs and across parallel workers.
- **Round_Trip**: The sequence `parse_oscal` → `serialize_oscal` → `parse_oscal` applied to a document.
- **OscalDoc_Facade**: The `OscalDoc` facade in `extensions/document.py` exposing `metadata`, `uuid`, `oscal_version`, `body`, and `assessment_period()`.
- **Builders**: The back-matter helper functions `make_hash`, `make_rlink`, and `make_resource` in `extensions/builders.py`.
- **Element_Validator**: The `validate_element` function in `extensions/validate_element.py`, whose supported type names are enumerated by `get_supported_element_types()`.
- **Leaf_Type**: An individual OSCAL element type accepted by the Element_Validator and listed by `get_supported_element_types()`.
- **AP_AR_Document**: An Assessment Plan or Assessment Results document, the only document types for which `assessment_period()` is defined.
- **Test_Matrix**: The existing Hatch parallel test matrix running Python 3.11 and Python 3.12.

## Requirements

### Requirement 1 — Hypothesis dependency setup

**User Story:** As a maintainer, I want Hypothesis available in the test environment, so that property-based tests run under the existing Hatch test harness.

#### Acceptance Criteria

1. THE PBT_Suite SHALL declare Hypothesis as a test dependency by enabling the `extra-dependencies` entry in the `[tool.hatch.envs.hatch-test]` configuration.
2. WHEN the Hatch test environment is created, THE PBT_Suite SHALL make the Hypothesis library importable in every cell of the Test_Matrix.
3. THE PBT_Suite SHALL leave all modules under `src/oscal_bindings/` unmodified.

### Requirement 2 — Corpus pinning

**User Story:** As a maintainer, I want corpus fixtures pinned to specific commits, so that test inputs are reproducible over time.

#### Acceptance Criteria

1. THE Corpus_Fetcher SHALL reference the NIST_Corpus by a specific commit SHA recorded in the PBT_Suite.
2. THE Corpus_Fetcher SHALL reference the AWS_Corpus by a specific commit SHA recorded in the PBT_Suite.
3. THE Corpus_Fetcher SHALL restrict AWS_Corpus documents to those located under the `component-definitions/` subdirectory.
4. THE Corpus_Fetcher SHALL expose NIST_Corpus documents covering the 7 OSCAL document types listed in the NIST_Corpus glossary entry, with mapping-collection documents supplied only by the Local_Corpus (Requirement 11).

### Requirement 3 — Corpus fetch, cache, and reuse

**User Story:** As a developer, I want corpus documents fetched once and cached locally, so that test runs are fast and do not repeatedly hit the network.

#### Acceptance Criteria

1. WHEN a corpus document is requested and is absent from the Corpus_Cache, THE Corpus_Fetcher SHALL download the document at the pinned commit SHA and store it in the Corpus_Cache.
2. WHEN a corpus document is requested and is present in the Corpus_Cache, THE Corpus_Fetcher SHALL return the cached document without performing a network request.
3. THE Corpus_Fetcher SHALL store the Corpus_Cache in a directory that is excluded from version control via `.gitignore`.

### Requirement 4 — Concurrency-safe fetching

**User Story:** As a developer running the parallel test matrix, I want corpus fetching to be safe under concurrent workers, so that parallel runs do not corrupt the cache or duplicate downloads.

#### Acceptance Criteria

1. WHILE multiple Test_Matrix workers request the same corpus document concurrently, THE Corpus_Fetcher SHALL ensure the document is downloaded at most once.
2. WHILE a download is in progress, THE Corpus_Fetcher SHALL prevent concurrent workers from observing a partially written cache entry.
3. WHEN concurrent requests for a cached document complete, THE Corpus_Fetcher SHALL return identical document content to every requesting worker.

### Requirement 5 — Hard-fail on unreachable corpus

**User Story:** As a maintainer, I want tests to fail loudly when a corpus is unreachable, so that missing inputs are never silently skipped.

#### Acceptance Criteria

1. IF the NIST_Corpus is unreachable at the pinned commit SHA and no cached copy exists, THEN THE Corpus_Fetcher SHALL raise an error that fails the dependent tests.
2. IF the AWS_Corpus is unreachable at the pinned commit SHA and no cached copy exists, THEN THE Corpus_Fetcher SHALL raise an error that fails the dependent tests.
3. IF a corpus fetch fails, THEN THE Corpus_Fetcher SHALL report the corpus name and the pinned commit SHA in the raised error.
4. THE PBT_Suite SHALL treat an unreachable corpus as a test failure rather than a skipped test.

### Requirement 6 — Round-trip invariant (corpus-seeded)

**User Story:** As a consumer of the bindings, I want parse and serialize to be lossless, so that documents survive a round trip without semantic change.

#### Acceptance Criteria

1. WHEN a NIST_Corpus, AWS_Corpus, or Local_Corpus document is subjected to a Round_Trip, THE PBT_Suite SHALL assert that the parsed model from the first parse equals the parsed model from the second parse.
2. WHERE a corpus document is structurally mutated before the Round_Trip, THE PBT_Suite SHALL apply the Round_Trip to the mutated document and assert the same equality property.
3. WHEN a corpus document is parsed with `parse_oscal` supplied as `bytes`, THE PBT_Suite SHALL assert the parsed model equals the model parsed from the equivalent `str` input.
4. IF `parse_oscal` raises during a Round_Trip on a corpus document, THEN THE PBT_Suite SHALL fail the test and report the offending document identifier.

### Requirement 7 — OscalDoc facade invariants

**User Story:** As a consumer of the facade, I want accessors to behave predictably on valid documents, so that I can rely on uniform metadata access.

#### Acceptance Criteria

1. WHEN the OscalDoc_Facade wraps a valid corpus document, THE PBT_Suite SHALL assert that accessing `metadata`, `uuid`, `oscal_version`, and `body` completes without raising.
2. WHEN the OscalDoc_Facade wraps an AP_AR_Document, THE PBT_Suite SHALL assert that `assessment_period()` returns a value without raising.
3. IF `assessment_period()` is invoked on a document that is not an AP_AR_Document, THEN THE PBT_Suite SHALL assert that `OscalAccessError` is raised.

### Requirement 8 — Builder invariants

**User Story:** As a consumer of the builders, I want generated back-matter to be schema-valid, so that constructed resources parse correctly.

#### Acceptance Criteria

1. WHEN `make_hash` is invoked with Hypothesis-generated inputs, THE PBT_Suite SHALL assert that the produced element is schema-valid back-matter content.
2. WHEN `make_rlink` is invoked with Hypothesis-generated inputs, THE PBT_Suite SHALL assert that the produced element is schema-valid back-matter content.
3. WHEN `make_resource` is invoked with Hypothesis-generated inputs, THE PBT_Suite SHALL assert that the produced element is schema-valid back-matter content.
4. THE PBT_Suite SHALL generate builder inputs using Hypothesis strategies and SHALL NOT synthesize full OSCAL documents.

### Requirement 9 — validate_element invariants

**User Story:** As a consumer of element validation, I want every supported element type to validate round trips of synthetic leaf inputs, so that the validator stays consistent with its declared supported types.

#### Acceptance Criteria

1. THE PBT_Suite SHALL enumerate Leaf_Types under test from the return value of `get_supported_element_types()`.
2. WHEN the Element_Validator validates a Hypothesis-generated Leaf_Type input, THE PBT_Suite SHALL assert that the validated result round-trips back to an equivalent value.
3. IF `validate_element` is invoked with an element type name absent from `get_supported_element_types()`, THEN THE PBT_Suite SHALL assert that `OscalParseError` is raised.
4. THE PBT_Suite SHALL generate Leaf_Type inputs using Hypothesis strategies and SHALL NOT synthesize full OSCAL documents.

### Requirement 10 — CI and matrix compatibility

**User Story:** As a maintainer, I want the property-based tests to run cleanly across the existing matrix, so that CI coverage extends to both supported Python versions.

#### Acceptance Criteria

1. THE PBT_Suite SHALL execute within the existing pytest configuration under `testpaths = ["tests"]`.
2. THE PBT_Suite SHALL pass on both Python 3.11 and Python 3.12 cells of the Test_Matrix.
3. WHILE the Test_Matrix runs with `parallel = true`, THE PBT_Suite SHALL complete without cache contention failures.
4. WHERE Hypothesis emits a failing example, THE PBT_Suite SHALL surface the counterexample in the pytest output.

### Requirement 11 — Local opt-in corpus

**User Story:** As a maintainer holding a Mapping Collection document that cannot be published, I want to point the PBT_Suite at that document through an environment variable, so that mapping-collection parsing is exercised locally without the document ever entering the public repository or its distributions.

#### Acceptance Criteria

1. WHEN the Local_Corpus_Variable holds an absolute path to a single JSON file, THE Corpus_Fetcher SHALL treat that file as the sole Local_Corpus candidate.
2. WHEN the Local_Corpus_Variable holds an absolute path to a directory, THE Corpus_Fetcher SHALL treat every file matching `**/*.json` under that directory as a Local_Corpus candidate.
3. THE Corpus_Fetcher SHALL apply the OSCAL_Root_Key_Filter to Local_Corpus candidates and SHALL expose each retained document with corpus name `local` and the matched root key.
4. WHERE the Local_Corpus_Variable names a directory, THE Corpus_Fetcher SHALL set each Local_Corpus document identifier to the document's path relative to that directory.
5. WHERE the Local_Corpus_Variable names a single file, THE Corpus_Fetcher SHALL set the Local_Corpus document identifier to the file's base name.
6. THE Corpus_Fetcher SHALL read Local_Corpus documents in place from the configured path without performing a network request and without writing to the Corpus_Cache.
7. THE PBT_Suite SHALL keep every Local_Corpus document outside the repository working tree, reading the document only from the external path held in the Local_Corpus_Variable.
8. IF the Local_Corpus_Variable is unset, THEN THE Corpus_Fetcher SHALL expose an empty Local_Corpus.
9. IF the Local_Corpus_Variable is unset, THEN THE PBT_Suite SHALL skip the mapping-collection coverage check with a skip reason that names `OSCAL_BINDINGS_LOCAL_CORPUS` and is visible in pytest output.
10. WHILE the Local_Corpus_Variable is unset, THE PBT_Suite SHALL run every test other than the mapping-collection coverage check, with Requirement 5.4 continuing to govern the NIST_Corpus and AWS_Corpus.
11. IF the Local_Corpus_Variable is set and the configured path is missing or unreadable, THEN THE Corpus_Fetcher SHALL raise an error that names `OSCAL_BINDINGS_LOCAL_CORPUS` and fails the dependent tests.
12. IF the Local_Corpus_Variable is set and the configured path yields zero documents after the OSCAL_Root_Key_Filter, THEN THE Corpus_Fetcher SHALL raise an error that names `OSCAL_BINDINGS_LOCAL_CORPUS` and fails the dependent tests.
13. IF the Corpus_Fetcher raises a Local_Corpus error, THEN THE Corpus_Fetcher SHALL exclude Local_Corpus document content from the error message.
14. WHILE the Local_Corpus_Variable is set to a valid source, THE PBT_Suite SHALL include Local_Corpus documents in the corpus pool sampled by the round-trip properties (Requirement 6) and the facade properties (Requirements 7.1 and 7.3).
15. WHILE the Local_Corpus_Variable is set to a valid source, THE PBT_Suite SHALL assert that the corpus pool contains at least one mapping-collection document.
